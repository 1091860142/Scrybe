# 技术方案

> 状态：已实现 · 最后更新：2026-08-12

## 1. 总体架构

三层结构，UI 与核心完全解耦：

```
app/ui/          界面层（PySide6）—— 主窗口 / 列表模型 / 设置 / 工作线程
app/core/        核心层 —— 管线编排、转码、切块、SRT 生成（无 Qt 依赖）
app/providers/   服务层 —— 识别服务抽象基类 + 各家实现
```

- 依赖方向：`ui → core → providers`，`core` 不依赖 `ui`，`providers` 不依赖 `core`。
- 数据模型集中在 `app/models.py`，各层共享（`FileJob`、`Segment`、`ProviderResult`、`FileStatus`）。

## 2. 技术选型

| 组件 | 选型 | 理由 |
| --- | --- | --- |
| GUI | PySide6 (Qt6) | 跨平台、`QAbstractTableModel` 数据驱动列表、`QThread`+Signal 线程模型 |
| 音视频解码 | PyAV（内置 FFmpeg 库） | 无需安装外部 ffmpeg，绿色分发 |
| 百炼识别 | dashscope SDK（WebSocket 流式） | 官方 SDK，直接传本地文件，句子级毫秒时间戳 |
| OpenAI 兼容 | requests | 简单 HTTP，verbose_json 返回 segments |
| 打包 | PyInstaller（单文件、无控制台） | `build.ps1` + `build.spec` |

## 3. 模块职责

| 模块 | 职责 |
| --- | --- |
| `config.py` | 配置 dataclass + `%APPDATA%\Scrybe\config.json` 原子读写（临时文件 + `os.replace`） |
| `pipeline.py` | 单文件管线：`extract()` 提取音频（带缓存）→ `recognize()` 切块识别写 SRT |
| `audio_util.py` | PyAV 统一转码为 **16kHz 单声道 s16 PCM WAV**（约 1.875MB/分钟），供各服务通用 |
| `audio_chunker.py` | 按时长切 WAV，用**帧数**计算精确累计偏移（最后一块天然偏短） |
| `srt_builder.py` | `Segment` 排序、去空、阈值合并、生成标准 SRT 文本 |
| `wav_util.py` | 纯 RIFF 头解析读时长（fmt 块 byte_rate + data 块长度），无需 ffprobe |
| `worker.py` | 队列工作线程：两阶段编排，Signal 通知 UI |

## 4. 数据流

### 4.1 单文件处理

```
媒体文件
  │  extract()（可并行，WAV 缓存于 %TEMP%\Scrybe_cache\<hash>.wav）
  ▼
16kHz 单声道 WAV
  │  recognize()：
  │    - 超过 provider 上限 → split_wav() 切块
  │    - 逐块 transcribe_wav()（串行，块偏移累加）
  ▼
Segment[]（start_ms / end_ms / text）
  │  segments_to_srt()（排序/去空/阈值合并）
  ▼
<源文件名>.srt（UTF-8 with BOM）
```

### 4.2 队列两阶段（worker.run）

```
阶段1  并行提取：ThreadPoolExecutor(max_workers=parallel_extractions)
         每个任务 pipeline.extract() → wav_of[idx] 或 failed[idx]
阶段2  串行识别：for idx in 队列顺序:
         跳过已成功；wav 缺失 → 标记失败；否则 pipeline.recognize()
         （识别的块内循环同样串行）
```

关键点：**音频提取并行、API 识别串行**。识别阶段按队列顺序逐个进行，一个返回字幕后才识别下一个，避免同时占用 API 导致限流/乱序。

## 5. 关键设计决策

### 5.1 音频提取缓存
- 提取后的 WAV 以源文件绝对路径的 SHA-1 前 16 位命名缓存于 `%TEMP%\Scrybe_cache`。
- **作用**：识别失败点「重试失败」时直接复用缓存，跳过转码，秒级进入识别。
- **幂等**：`extract()` 检测缓存存在且非空则直接返回；先写 `.tmp` 再 `os.replace` 原子发布。
- **清理**：主窗口 `closeEvent` 时删除整个缓存目录。
- 注意：缓存按路径而非内容，同一路径被替换内容后仍命中旧缓存（当前场景可接受）。

### 5.2 Provider 抽象
```python
class ASRProvider(ABC):
    def capability(self) -> ProviderCapability   # 声明单次上传上限，驱动是否切块
    def transcribe_wav(self, wav_path, language, log, stop) -> ProviderResult
def create_provider(cfg) -> ASRProvider          # 工厂：按 cfg.provider 分发
```
- `ProviderCapability.max_file_size_bytes=None` 表示无上限（百炼流式），否则驱动切块。
- `ProviderResult` 内部时间统一为**整数毫秒**，各 provider 在返回前完成单位换算。
- 新增服务：实现该接口 + 在工厂注册即可，UI/管线零改动。

### 5.3 线程模型
- `QThread` + 常驻 `QueueWorker`（`moveToThread`），worker 内部用 `ThreadPoolExecutor` 做提取并行。
- 所有耗时操作都在 worker 线程；UI 只通过 Signal 接收更新（`log` / `file_started` / `file_progress` / `file_done` / `queue_progress` / `queue_finished` / `queue_phase`）。
- 停止：`threading.Event` 跨线程协作检查，worker 在提取循环、识别循环、网络退避各点检查。

### 5.4 切块偏移合并
- 切块时用帧数（`frames_read * 1000 // bytes_per_sec`）计算每块精确时长，保证累计偏移无累积误差。
- 识别结果每个 Segment 的 `start_ms/end_ms` 加上块起始偏移后合并，保证整段时间轴连续。

### 5.5 已成功任务跳过
- 点击「开始转换」只处理未完成任务；已成功任务保留状态直接跳过（`reset_statuses` 不再重置成功项），避免第二批导入后重复识别第一批。

## 6. 配置项

见 [app/config.py](../app/config.py)。常用项：`provider`、`language`、`output_dir`、`chunk_seconds`（切块时长）、`merge_gap_ms`（合并阈值）、`parallel_extractions`（并行提取数）。

## 7. 打包

- `build.ps1`：装依赖 → `pytest` → `PyInstaller --noconfirm --clean build.spec`。
- `build.spec`：单文件（`EXE` 一个文件）、`console=False`；`collect_all("av")` 与 `collect_all("dashscope")` 收集动态导入与内置 FFmpeg DLL。
- 已知警告：dashscope 的 `finetune.reinforcement` 子模块依赖可选 `pydantic`/`yaml`，不影响识别功能，可在 spec 中排除以减小体积（待办）。
